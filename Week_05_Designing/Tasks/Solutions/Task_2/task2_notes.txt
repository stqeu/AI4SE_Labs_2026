UPDATE #1 - 2026-10-29 - ADR first draft created
-------------------------------------------------
Why I asked for it:
- Turn the exploration in notes.txt (sections 0-10) into a formal Architecture
  Decision Record that chooses an architecture for NFFH, in a standard format,
  without diagrams or tables yet so I can review the text first.

What changed in the ADR (new document, v1):
- Format: Nygard-style ADR extended with MADR's "decision drivers" and
  "considered options".
- Status: Proposed, pending team review.
- Context: system summary, 3 roles, 5 capability groups mapped to story numbers,
  scope/constraints (small region, 3 students, ~3 months, low budget, web only),
  technical forces (atomic stock, ownership authz, safe deletes, revocable
  "remember me", inexperienced team).
- Decision drivers (priority order): deliverability, security under
  inexperience (fail closed), consistency, low cost/ops, visible+testable
  design, evolvability.
- Considered options: A modular monolith, B microservices, C serverless/BaaS,
  each with a short description + good/bad.
- Decision: A, "renting the boring parts" (managed Postgres + managed host +
  framework security module). C = runner-up, B = rejected.
  8 binding rules: modules, layers, auth via framework module, server-side
  sessions + HttpOnly cookie + CSRF, service-layer role+ownership authz,
  conditional UPDATE for stock + CHECK constraint, data rules (NUMERIC money,
  price snapshot, DATE pickup, soft delete), Maps via lat/lng URL.
- Rationale: why not B; why A over C (consistency, security wording from
  notes section 10, course fit, cost/lock-in, evolvability); what C does better
  and how renting the boring parts closes the gap.
- Consequences: positive, negative, risks + mitigations (overselling, IDOR,
  mass assignment, auth mistakes, schedule overrun).
- Conditions to revisit: when to switch to C, when to move toward B, and that
  the security claim depends on using the framework auth module.
- Open issues (8 checklist items) carried over from notes section 2.

Decisions/assumptions I made while drafting (please confirm):
- Assumed "complete order" reserves stock immediately.
- Proposed one order per farm for multi-farm carts (each with own pickup date).
- Put "build the order/stock/authz core first, admin CRUD last" as a schedule
  mitigation.

Questions for review:
1. Which backend framework does the team know best? (Fills the first open
   issue and makes binding rule 3 concrete.)
2. Should the ADR stay as one ADR, or should follow-ups (e.g. multi-farm
   cart, session strategy) become separate ADRs (ADR-002, ADR-003...)?
3. Is the level of implementation detail in "Decision" (binding rules) right,
   or should some of it move to a later design document?
