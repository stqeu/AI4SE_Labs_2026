1. CANDIDATE ARCHITECTURES - OVERVIEW (exchange #1)
Q (me): Propose 3 genuinely different architectures.
Axis: how the backend is split, and who runs it.

1a. Layered modular monolith
  - One deployable app (+ one relational DB); code split into modules A-F; layers
    controller -> service -> repository.
  - First impression: natural fit for 3 people / 3 months; one DB transaction covers
    "complete order + decrement stock".

1b. Microservices behind an API gateway
  - Separate services (Identity, Catalogue, Orders, Admin/Reporting), each with its
    own DB; gateway does auth + routing.
  - First impression: textbook-impressive but the key flow (order) crosses services
    -> distributed consistency + lots of ops for a tiny team.

1c. Serverless / BaaS (e.g. Supabase or Firebase + thin frontend + a few functions)
  - Managed auth + DB; authorisation as DB rules (row-level security); custom logic
    only where needed (complete order).
  - First impression: fastest to a working demo, cheapest to host; risk = security
    lives in rules that are easy to get subtly wrong; vendor lock-in.
